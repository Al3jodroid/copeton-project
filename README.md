# Copetón — Code & Orchestration Protocol for Engineering, Testing & Operations

## Purpose of This Repository
**Copetón** (**C**ode & **O**rchestration **P**rotocol for **E**ngineering, **T**esting & **O**peratio**N**s) is a production-grade **AI Engineering Execution Framework** comprising 10 generalized instruction files located inside the `stages/` folder (`stages/s0_repository_setup.md` through `stages/s9_deployment_release.md`) and standardized technical templates organized inside the `templates/` directory.

Their purpose is to act as **strict, step-by-step execution prompts** to guide an AI assistant through bootstrapping and building *any* production application from scratch using professional software engineering practices.

Instead of just asking the AI to "write code," these files configure the AI to function as an automated engineering partner—adhering to technical design contracts, deploying reusable skill extensions, and operating as an automated code auditor and security blocker.

## Repository Architecture & Lifecycle

This repository is designed as a **GitHub Template Repository (Starter Kit)**. 

### 1. Template State (Initial GitHub Repository)
Before launching development on a specific application, the root repository contains only the framework instructions, templates, and documentation:

```text
copeton-project/
├── README.md               # Framework landing page
├── templates/              # Categorized production Markdown templates (including business_brief.md)
└── stages/                 # Stage instruction prompts (s0_repository_setup.md to s9_deployment_release.md)
```

### 2. Application Execution State (Generated by Stage 0)
When an engineer initializes a new application project using this template, the AI assistant executes `stages/s0_repository_setup.md`. **Stage 0 automatically provisions `/src`, `/docs`, `.ai/`, `.gitignore`, and `engineering_roadmap.md` at the root level:**

```text
copeton-project/                    # Active Application Repository
├── README.md               # Project overview & tech stack specifications
├── engineering_roadmap.md  # Active engineering roadmap (copied from templates/execution/)
├── stages/                 # In-repo development manual & stage instruction prompts
├── templates/              # Categorized base Markdown templates
├── .gitignore              # Stack-specific ignore rules
├── .ai/                    # Active AI extensions (.ai/skills/, .ai/agents/)
├── docs/                   # System architecture contracts, specs, ADRs & business_brief.md
└── src/                    # 👈 ALL APPLICATION SOURCE CODE LIVES HERE!
    ├── modules/
    ├── components/
    └── main.dart (Flutter) / MainActivity.kt (Android) / main.ts
```

- **Source Code Placement:** All application business logic, models, controllers, and APIs reside strictly inside **`/src/`**.
- **Documentation Placement:** All human-readable team documentation (active specifications, business requirement briefs like `business_brief.md`, protocol guides like `change_management.md`, threat models, and ADRs) reside inside **`/docs/`**.
- **AI Infrastructure Placement:** All AI prompt contracts, skill extensions, and cached document blueprints reside inside **`.ai/`** (`.ai/agents/`, `.ai/skills/`, `.ai/templates/`).
- **Stage Instruction Suite:** The `/stages/` and `/templates/` directories remain in the repository as the **built-in development manual & master blueprint vault** that guides the AI assistant through every development milestone.

## The Core Methodology
By feeding these files to your AI sequentially, it is forced to adhere to two critical engineering principles:

1. **Spec-Driven Development (SDD):** The AI must read the product vision in `business_brief.md`, write a technical behavioral specification (inputs, outputs, edge cases), and generate automated tests *before* it is allowed to write any implementation code.
2. **The Agentic Work Cycle:** The AI must explicitly pause and await lead engineer approval before writing logic. The cycle is: **Explore** (read context), **Plan** (write spec/design), **Approve** (wait for the lead engineer), **Delegate** (execute code), and **Verify** (run tests).

## Commit Message Convention (Scoped Conventional Commits)
All changes committed during development must follow the **Scoped Conventional Commits** format:

```text
<type>(<scope>): <short description in imperative mood>
```
- **`<type>`:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `security`.
- **`<scope>`:** Stage milestone (e.g. `stage-0`), Feature/Module (e.g. `auth`, `parser`, `core`), or Issue ID (e.g. `PROJ-101`).
- **Examples:**
  - `chore(stage-0): bootstrap repository architecture and persistent AI rules`
  - `feat(core): implement core business logic module using SDD`
  - `security(auth): enforce multi-tenant isolation rules`

### Remote Git Pushing Strategy (3 Delivery Levels)
- **Level 1 — Daily Feature Commits:** Pushed regularly during development (`git push origin main`).
- **Level 2 — Stage Milestone Tags:** Pushed upon completing a stage prompt (`git tag -a v1.0-stageX -m "Stage X complete" && git push origin v1.0-stageX`).
- **Level 3 — Production Release Tags:** Pushed upon production delivery to trigger Stage 9 CI/CD deployment pipelines (`git tag -a v1.0.0 -m "Release v1.0.0" && git push origin v1.0.0`).

## How to Use These Files
To build your application, feed these instruction files to your AI assistant **one by one, sequentially**:

1. Start your AI assistant in your project working directory.
2. Populate or review `templates/docs/business_brief.md` to define your product goals.
3. Provide the AI with `stages/s0_repository_setup.md`. The AI will set up your project structure, copy standard templates from `/templates/` into `.ai/templates/`, and initialize `engineering_roadmap.md`.
4. Once the AI marks Stage 0 as complete in `engineering_roadmap.md`, feed it `stages/s1_system_architecture.md`. The AI will read `business_brief.md` to design system architecture and technical specifications.
5. Continue this process Stage by Stage. The AI will read each instruction file, ask for your approval on architectural decisions, write code, run tests, and commit changes using Scoped Conventional Commits.

### Tailoring & Skipping Non-Required Stages
Not every application requires all 10 stages (e.g., a single-agent utility app may not require Stage 4 Multi-Agent Pipelines). 
- **Stage Customization Matrix:** During Stage 0 bootstrap, review the **Project Stage Tailoring Matrix** inside `engineering_roadmap.md`. Mark non-applicable stages as `[N/A]` with a short rationale.
- **Automated Skip Protocol:** When an instruction prompt for a skipped stage is provided, the AI detects the `[N/A]` status, logs the skip rationale, creates the stage closing commit/tag, and advances to the next stage without unneeded overhead.

### Adding New Features Mid-Project (Feature Change Protocol)
When adding new features or modifying requirements after initial bootstrap:
- Follow the protocol defined in `/docs/change_management.md` (copied from `templates/docs/change_management.md`).
- Classify the change (Class A Small, Class B Medium, Class C Major).
- Update `/docs/business_brief.md`, write a technical spec in `/docs/specs/`, record the feature iteration under the active stage in `engineering_roadmap.md`, obtain approval, and write tests before implementation code.

## "Trust but Verify"
Remember, the AI proposes, but the lead engineer decides. Even with these strict instructions, you must read the generated diffs, review the test coverage, and validate the architecture before giving the AI the green light to move to the next stage.
